# 自适应扳机协议综述（跨厂商通用）

本文把"力反馈 / 自适应扳机"这一类手柄功能的协议结构抽象出来，作为后续厂商具体分析的
共同框架。所有内容均为**结构层面的通用建模**，不涉及任何一家的具体实现。

## 一、什么是自适应扳机

自适应扳机指手柄扳机能在不同行程位置提供可编程的**阻力 / 段落感 / 震动**，让游戏里的
"拉弓 / 扣枪 / 踩油门"等动作有对应的物理反馈。主流实现把扳机手感拆成几类语义：

| 语义 | 英文常见命名 | 行为 |
|---|---|---|
| 阻尼 | Race / Damper | 行程某段内线性阻力，可设起止位置与力度 |
| 振动 | Vibration | 周期性震动，可设频率与振幅 |
| 射击 | Shot / Kick | 某点突入式段落阻力，可设突破位置与行程 |
| 锁定 | Lock | 行程被锁定/解锁 |
| 常规 | Normal | 无特殊手感 |

不同厂商把这些语义映射到各自的"模式编号"，编号体系并不统一（例如 A 家用 0–5 连续编号，
B 家用 0–13 的更细枚举并区分"扳机类型"家族）。这正是需要一张**语义 ↔ 厂商编号**映射表的原因。

## 二、配置对象的通用结构

无论哪家，手柄配置在 UI 层通常是一个对象，关键字段包括：

- **模式 / 类型 / 预设 id**：决定这一侧扳机走哪套手感模型（阻尼 / 振动 / 射击）及其预设参数。
- **参数族**：每种手感模型各带一组参数，例如阻尼族含 `{起始位置, 力度}`，振动族含
  `{起始位置, 力度, 起始力度, 频率, 输出开关}`，射击族含 `{突破位置, 阻力, 行程, 输出开关}`。
- **行程区间**：扳机有效行程的起止百分比。
- **左右对称**：左、右扳机各一份上述结构，连续排放。

## 三、传输层通用范式

配置对象经"位域打包"变成连续字节缓冲区（配置 blob），再通过 HID 输出报告下发：

```
[报告ID] [操作码] [地址/块索引] [长度] [数据…] [校验]
```

典型特征：

- **报告 ID** 固定（例如 0x02）。
- **操作码** 区分 get / set / 读基信息等；常以 `cmd | (class<<4) | (type<<6)` 形式编码。
- **分块同步**：blob 较大时按固定粒度（例如 48 字节）分块，仅上传发生变化的块，
  每块记录"脏标记"，避免每次全量下发。
- **校验** 多为字节累加和（sum16）或简单异或。

## 四、为什么需要映射表

游戏侧只表达抽象的"开枪 / 开车 / 拉弓"语义；手柄侧需要具体的厂商指令。中间层应当：

1. 只认**语义**（阻尼 / 振动 / 射击 …）。
2. 输出时查**厂商适配表**翻译成对应编号与参数。
3. 新增一家手柄 = 只加一张表，不动引擎。

这样，哪怕游戏不给任何触觉数据，也能用参数模型生成"兜底手感"，而不是干等厂商适配。
