# 厂商乙：力反馈扳机协议（结构层面 + 偏移还原）

> 厂商乙 = 采用"力反馈扳机"方案的某国产手柄厂商（带原生配置下发协议）。
> 本文只描述我们**逆向得到的协议结构与字段偏移**，不出现任何可被反查到真名的字符串，
> 也不包含任何闭源程序二进制、源码或字符串转储。

## 一、配置 blob 总览

厂商乙的扳机配置使用一段**固定长度**的字节缓冲区（配置 blob），本研究还原出其长度为
**720 字节**。该长度与厂商配置界面自身声明的"配置 blob 大小"完全吻合，可作为偏移还原正确性的
交叉验证。

## 二、位域打包与偏移还原

配置界面把一个配置对象按字段 bit 数**位域打包**进 blob。我们复刻了 UI 侧的打包器
（见 [`tools/bitpack_offset_calc.py`](../tools/bitpack_offset_calc.py) 的通用实现），
喂入同一份 schema，得到每个字段在 720 字节 blob 里的绝对字节偏移。

### 扳机三元组（核心结果）

左右扳机各一份连续的三字节组 `(模式, 类型, 预设id)`：

| 字段 | blob 字节 | 位宽 |
|---|---|---|
| 左扳机 模式 | 404 | 8 |
| 左扳机 类型 | 405 | 8 |
| 左扳机 预设id | 406 | 8 |
| 右扳机 模式 | 457 | 8 |
| 右扳机 类型 | 458 | 8 |
| 右扳机 预设id | 459 | 8 |

这与原生层观测到的对象布局**方向一致**（左右扳机各一组连续三元组），互相印证。

### 单只扳机的完整配置块

每只扳机的配置块 = 三元组(3B) + 跟随开关(1b) + 阻尼族 + 振动族 + 射击族，约 57 字节，
左右各一份连续排放。

## 三、语义枚举（厂商乙侧）

厂商乙把扳机"模式"细分为一个较长的枚举（约 0–13），覆盖：

- 常规、重卡、卡丁车、跑车、扳机锁、弓箭、重剑、拳、棍棒、机枪、蓄能枪、手枪、狙击、振动。

并把扳机"类型"分为三个家族：

- **0 = 阻尼（线性阻力）**
- **1 = 振动**
- **2 = 射击（突入式段落）**

`预设id` 在族内取固定值（例如"扳机锁"与"振动"各有固定的 id 常量）。

## 四、参数模型

每种手感家族带一组参数（均为 8 位字段）：

- **阻尼族** `{起始位置, 力度}` × 4 个预设（对应重卡 / 卡丁 / 跑车 / 扳机锁）。
- **振动族** `{起始位置, 力度, 起始力度, 频率, 输出开关}` × 5 个预设（弓箭 / 重剑 / 机枪 / 蓄能枪 / 振动）。
- **射击族** `{突破位置, 阻力, 行程, 输出开关}` × 4 个预设（拳 / 棍棒 / 手枪 / 狙击）。

这些参数模型可直接用于"游戏未下发触觉数据时"的兜底手感生成。

## 五、传输层

- **报告 ID** 固定为 `0x02`。
- **操作码** 形如 `cmd | (class<<4) | (type<<6)`；常见命令：读=0x12、写=0x22(+type<<6)、
  读基信息=0x15、读键事件=0x25、功能复位=0x36。
- **地址粒度** 16 字节；**分块同步**粒度 48 字节（仅上传变化块，按块记脏）。
- **校验** 为字节累加和（sum16）。

## 六、与门禁的关系

厂商乙的配置程序在枚举设备时校验 VID/PID 与 usagePage，门禁公式形如
`(usagePage - 0x8000) & ~0x04 == 0`。这属于**枚举层**，与 blob 字段偏移无关；但门禁一旦
被绕过（无需真实硬件即可伪造一台被识别的设备），就能让配置程序把真实配置帧发到"假设备"，
从而捕获实际字节——这正是本研究无需硬件的关键前提。
